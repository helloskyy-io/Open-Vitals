# OpenVitals Data Ingestion Plan

## Bronze, Silver, Gold Architecture

This document defines the official data ingestion and storage
architecture for OpenVitals. It follows industry-standard Bronze,
Silver, Gold data lake principles adapted for personal health data
ownership.

------------------------------------------------------------------------

# Overview

OpenVitals uses a layered architecture to ensure:

-   Full preservation of original vendor data
-   Reproducible, vendor‑agnostic structured datasets
-   Transparent analytics and comparison
-   Future extensibility for AI and platform features

Layers:

0.  Evidence Archive (optional)
1.  Bronze Layer --- Raw Data Lake
2.  Catalog Layer --- Metadata & Discovery
3.  Silver Layer --- Canonical Structured Data
4.  Gold Layer --- Analytics & Metrics
5.  Platform Layer --- UI, APIs, Automation
6.  AI Layer --- Interpretation and Prediction

------------------------------------------------------------------------

# Layer 0 --- Evidence Archive (Optional)

Purpose: Preserve original export files exactly as provided by vendors.

Path example:

data/raw_exports/google_fit/export_2026‑03‑01.zip

Characteristics:

-   Original zip files unchanged
-   Used for audit, recovery, and debugging
-   May be rotated or deleted over time

This is not the primary data lake.

------------------------------------------------------------------------

# Layer 1 --- Bronze Layer (Raw Data Lake)

Purpose: Permanent, deduplicated storage of all raw vendor files.

Path example:

data/raw_store/google_fit/`<content_hash>`{=html}/file.csv

Characteristics:

-   Files stored in original format (CSV, JSON, XML, TCX, etc)
-   No normalization
-   No modification
-   Content‑addressed (hash‑based) to prevent duplication

Temporal workflow responsibilities:

-   Extract new vendor exports
-   Compute file hashes
-   Copy only unique files
-   Register files in metadata catalog

This layer ensures:

-   Complete data preservation
-   Vendor‑agnostic raw storage
-   Future reprocessing capability

------------------------------------------------------------------------

# Layer 2 --- Catalog Layer (Metadata and Discovery)

Purpose: Fast discovery and understanding of raw data structure.

Stored in Postgres database.

Example tables:

files

-   file_id
-   vendor
-   path
-   hash
-   size
-   type
-   export_id

file_schema_profile

-   file_id
-   detected_columns
-   detected_json_keys
-   detected_xml_tags
-   inferred_time_range

This layer enables:

-   Fast search for specific signals
-   Automated schema discovery
-   Rapid ingestion pipeline development
-   Identification of new or changed vendor formats

This layer is critical for managing vendor complexity.

------------------------------------------------------------------------

# Layer 3 --- Silver Layer (Canonical Structured Data)

Purpose: Vendor‑agnostic, normalized health dataset.

Example tables:

heart_rate_samples

-   timestamp
-   bpm
-   source
-   device
-   provenance

sleep_sessions

step_events

Characteristics:

-   Structured
-   Clean
-   Queryable
-   Vendor‑agnostic

Generated by Temporal ingestion workflows.

This is the primary dataset used for analytics.

------------------------------------------------------------------------

# Layer 4 --- Gold Layer (Metrics and Analytics)

Purpose: Derived metrics and analytical outputs.

Example tables:

daily_steps

daily_sleep_duration

daily_resting_hr

comparison_results

Characteristics:

-   Aggregated
-   Computed
-   Optimized for visualization and reporting

Used for:

-   Class project results
-   Graph generation
-   Scientific comparison
-   User dashboards
